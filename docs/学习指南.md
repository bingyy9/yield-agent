# FAgent 学习指南（零基础版）

这份指南假设你：会一点编程（看得懂 if / for / 函数），但**不懂芯片制造，也没写过 Agent**。
跟着走完，你应该能讲清楚三件事：

1. 这个 demo 在解决工厂里的什么问题；
2. 一个「Agent」到底是怎么工作的；
3. 你在页面上点一下，代码里依次发生了什么。

## 2. 业务小白课：存储芯片工厂在查什么

### 2.1 晶圆和 die：一张披萨切成很多小块

- **晶圆（wafer）**：一张圆形的硅片，直径 300mm，像一张披萨。
- **die**：晶圆上切出来的一个个小方块，每块将来就是一颗芯片。本 demo 里每片晶圆有 **626 颗 die**（`src/lib/fab/core.ts` 的 `SITES`）。
- **DRAM**：内存芯片。每个存储单元 = **1 个晶体管 + 1 个电容**。电容里有电荷代表 1，没电荷代表 0。电容会慢慢**漏电**，所以内存要定时刷新。如果某个电容做坏了、漏得太快，刷新前数据就丢了，这叫**数据保持失效**。这是本 demo 主案例的「症状」。

### 2.2 批次、工序、设备、腔体

- **批次（lot）**：25 片晶圆装一个盒子，一起在工厂里走。批次号像 `N3B417`，片号是 1~25（槽位 slot），所以 `N3B417.03` 就是这盒的第 3 片。
- **工序（step）**：一片晶圆要经过几百道工序。demo 简化成 8 道（`core.ts` 的 `ROUTE`），比如「存储节点刻蚀」「CMP 研磨」「TiN 沉积」。
- **设备（tool）和腔体（chamber）**：一台设备（如 `ETCH-07`）里有好几个腔体（A、B、C）。同一批的 25 片晶圆会**轮流**进不同腔体：1 号进 A、2 号进 B、3 号进 C、4 号又进 A……
  - 所以如果你发现坏片总是「每隔几片坏一片」，就很可能是某一个腔体出了问题。

### 2.3 CP 测试、Bin、良率

- **CP 测试**：晶圆做完后，探针台逐颗 die 通电测试。
- **Bin**：测试结果分档。demo 用 8 档：

  | Bin | 含义 | 算好吗 |
  | --- | --- | --- |
  | 1 | 良品 | ✅ |
  | 2 | 修复良品（坏了几行，用备用行修好了） | ✅ |
  | 3 | 开路 / 短路 | ❌ |
  | 4 | IDD 漏电（静态电流过大） | ❌ |
  | 5 | 时序不过 | ❌ |
  | 6 | 阵列坏太多、修不好 | ❌ |
  | 7 | 数据保持失效（电容漏电） | ❌ |
  | 8 | 其他 | ❌ |

- **良率** =（Bin 1 + Bin 2）÷ 总 die 数。最近正常水平（**基线**）约 **91.2%**（`core.ts` 的 `BASELINE_YIELD`）。
- **Bin 柏拉图（Pareto）**：把各种坏法按数量排序的柱状图，一眼看出「主要坏在哪一类」。N3B417 是 Bin 7 特别多：12.6%，基线只有 1.1%。

### 2.4 晶圆图：坏点的「指纹」

把每颗 die 的 Bin 按位置涂色，就是**晶圆图（wafer map）**。坏点的**空间形状**往往直接暴露是哪类工艺出了问题：

| 形状 | 常见原因 | demo 里的场景 |
| --- | --- | --- |
| 边缘一圈（边缘环） | 刻蚀 / 沉积在晶圆边缘不均匀 | N3B417：刻蚀腔体边缘刻不够 |
| 弧形细线（划伤） | CMP 研磨时颗粒刮伤 | N3B409：研磨头划伤 |
| 中心一团 | 沉积喷淋头中间堵了 | N3B412：中心薄膜偏薄 |
| 随机散点 | 正常的随机缺陷 | 正常批次 |

- **叠加图（stacked map）**：把 25 片的晶圆图叠在一起，每个位置算「坏的比例」，形状会更清楚。
- **径向分布**：从圆心到边缘分几圈，每圈算坏的比例。边缘环的曲线会在最右边翘起来。

### 2.5 共性分析：卡方检验和 p 值（直觉版）

问题：坏片到底跟哪台设备、哪个腔体有关？

做法（`commonality_analysis` 工具）：

1. 把所有已测晶圆分两类：**坏片**（Bin 7 比例 > 6%）和**好片**。
2. 对每个腔体画一个 2×2 的表：

   |  | 坏片 | 好片 |
   | --- | --- | --- |
   | 经过 ETCH-07 C | 21 | 25 |
   | 没经过 | 0 | 204 |

3. 问：**如果这个腔体跟坏片完全无关，出现这种分布的概率有多大？** 这个概率就是 **p 值**。
   - 主案例 p ≈ 6.6×10⁻²⁴，意思是「纯属巧合」的可能性几乎为零。
   - 一般 p < 0.01 就算显著。
4. 卡方（χ²）就是计算这个 p 值的一种标准方法，不用背公式，记住「**p 越小，越不像巧合**」。

> ⚠️ p 值小只说明「相关」，不证明「因果」。所以 Agent 还要去查设备日志和量测，把**物理机理**补上。这就是「证据链」。

### 2.6 设备日志和在线量测

- **PM（预防性保养）**：定期拆开设备换零件。换完要做**复机认证（requalification）**：先跑一批测试片，确认没问题才能放产品进去。
- 主案例的故事就藏在日志里：10-14 腔体 C 换了**聚焦环**（一个套在晶圆边缘的环），复机时偷懒了：只跑了 25 片测试片（SOP 要求 50 片），也**没测边缘 CD**。
- **在线量测（inline metrology）**：生产中途抽测的数据。比如 `SN_BOTTOM_CD` 是存储节点孔底部的宽度。孔底太窄 → 电容做小了 → 存的电荷少 → 数据保持失效。
- Agent 会对比「10-14 之前 vs 之后」腔体 C 的边缘 CD，确认确实变窄了，而且**只在边缘**变窄。和晶圆图的边缘环对上了。

### 2.7 FA 和 8D 报告

- **FA（Failure Analysis，失效分析）**：工厂里对问题的正式调查。demo 里有个历史案例库（`src/lib/fab/knowledge.ts`），Agent 会翻「以前有没有类似的」。
- **8D 报告**：业界标准的问题处理报告，demo 只写其中 5 个 D：
  - **D2 问题描述**：什么批次、什么症状、掉了多少良率。
  - **D3 围堵**：马上止血。还在生产线上、经过了问题腔体的晶圆先扣住，别让它继续往下做。
  - **D4 根因**：为什么坏，附证据。
  - **D5 纠正**：怎么修好（比如重新校准、补做复机认证）。
  - **D7 预防**：以后怎么不再发生（比如把「复机必须测边缘 CD」写进 SOP）。

### 2.8 把主案例串起来（N3B417）

```
良率 78.6%（基线 91.2%） ── 哪类坏？ ──▶ Bin 7 数据保持，是基线的 11 倍
        │
        ▼ 坏在哪？
晶圆图：边缘一圈 ──▶ 怀疑刻蚀或沉积的边缘问题
        │
        ▼ 跟哪台设备有关？
共性分析：ETCH-07 腔体 C，p = 6.6×10⁻²⁴
        │
        ▼ 那台设备发生了什么？
日志：10-14 换聚焦环，复机认证不合规；之后有 RF 告警
        │
        ▼ 物理上说得通吗？
量测：10-14 之后腔体 C 边缘 CD 变窄，中心正常
        │
        ▼ 以前见过吗？
FA 案例库：有相同机理的老案例，当时的纠正措施可以参考
        │
        ▼ 还有谁受影响？
5 个在制批次共 46 片经过了问题腔体 → 立即拦截
        │

```

**这就是一个良率工程师的标准思路，Agent 就是在模仿它。**

## 3. Agent 是什么

### 3.1 聊天机器人 vs Agent

- **聊天机器人**：你问一句，它凭记忆答一句。它没法查你工厂的数据库。
- **Agent**：你给它一个任务，它**自己决定**要查什么、调用哪个工具、看完结果再决定下一步，直到完成。

### 3.2 一个公式：Agent = LLM + 工具 + 循环

```
           ┌────────────────────────────────────────────┐
           │                                            │
 你的问题 ──▶  Claude 思考：「我该先查批次良率」             │
           │      │                                     │
           │      ▼ 输出一个「工具调用」请求                │
           │   get_lot_summary({lot_id: "N3B417"})      │
           │      │                                     │
           │      ▼ 我们的 TypeScript 代码真的去算        │
           │   { yield: 0.786, failBins: [...] }        │
           │      │                                     │
           │      ▼ 把结果还给 Claude                     │
           └──── Claude 再思考：「Bin 7 超标，看看晶圆图」 ◀┘
                  ...循环，直到 Claude 不再调用工具...
```

关键认知：**Claude 自己一个数都不算**。

- Claude 负责：**决定**下一步查什么、**解读**结果、**写**结论。
- 我们的代码负责：**真的去算**（读数据、做卡方检验、识别晶圆图形状）。

所以第 1 站那个问题的答案是：**图和数字是代码算的，查的顺序和文字结论是 AI 给的。** 这也是 Agent 可信的关键：数字可复现，不是 AI 编出来的。

### 3.3 工具 = 名字 + 说明 + 参数格式

Claude 怎么知道有哪些工具可用？我们每次请求都把「工具清单」发给它。每个工具三样东西（看 `src/lib/agent/tools.ts:47` 的 `listLots`）：

```ts
const listLots = {
  name: "list_lots",                          // 名字
  description: "列出 D1b LPDDR5 ... 所有批次……", // 说明：给 Claude 看的「使用说明书」
  schema: z.object({ status: ... }),          // 参数格式：用 zod 定义，自动转成 JSON Schema
  run({ status }) { ... },                    // 真正干活的函数（只在我们这边跑，Claude 看不到）
};
```

**description 写得好不好，直接决定 Claude 会不会用、用得对不对。** 它就是给 AI 的接口文档。

### 3.4 系统提示词 = 岗位说明书

`src/lib/agent/prompt.ts` 是一段约 30 行的中文，告诉 Claude：

- 你是谁（良率工程部的失效分析助手）；
- 背景知识（产品、Bin 定义、基线）；
- **调查方法**（8 步，和 2.8 节那张图一模一样）；
- 表达要求（调用工具前先说为什么、引用具体数字、不编数据）。

打开读一遍，你会发现它就像写给一个新入职工程师的培训材料。

### 3.5 两种模式：在线 vs 离线回放

| | 在线（live） | 离线回放（replay） |
| --- | --- | --- |
| 需要 | `ANTHROPIC_API_KEY` | 什么都不要 |
| 谁决定调哪个工具 | Claude 实时决定 | 剧本写死（`src/lib/agent/replay.ts`） |
| 工具结果 | **真实计算** | **真实计算**（同一个 `runTool`） |
| 能否追问 | 能 | 不能 |
| 代码 | `src/lib/agent/live.ts` | `src/lib/agent/replay.ts` |

**回放模式 = 用一段剧本「扮演」Claude**，但它调用的工具和在线模式完全是同一套。所以没有 Key 也能完整学习工具和前端部分。

## 4. 架构与一次请求的旅程

### 4.1 全景图

```
浏览器（React）                         服务器（Next.js）
┌──────────────────────┐   POST     ┌──────────────────────────────┐
│ workbench.tsx         │ ────────▶ │ app/api/agent/route.ts        │
│  run() 发请求          │           │   有 Key? ──是──▶ live.ts ◀──▶ Claude API
│  逐行读流 → onEvent    │ ◀──────── │          └─否──▶ replay.ts     │
│  reducer 更新界面      │  NDJSON 流 │                  │             │
│ views/charts/wafer    │           │                  ▼             │
│  画图                  │           │          agent/tools.ts runTool │
└──────────────────────┘           │                  │             │
                                    │                  ▼             │
                                    │   lib/fab/*（模拟工厂 + 统计）   │
                                    └──────────────────────────────┘
```

### 4.2 一次请求的 10 步（带文件位置）

以「点击 N3B417」为例：

1. **页面加载**：`src/app/page.tsx` 在服务端生成左侧批次卡片，并检查有没有 API Key（`liveAvailable`）。
2. **点击**：`src/components/workbench.tsx:152` 的 `run()` 被调用，把你的问题加入对话（`dispatch({type:"user"})`）。
3. **发请求**：`workbench.tsx:163` 用 `fetch("/api/agent")` 发 POST，body 是 `{prompt, history, turn, forceReplay}`。
4. **服务端接收**：`src/app/api/agent/route.ts:23` 的 `POST`。它创建一个**流**，先发一个 `{type:"mode"}` 事件告诉前端当前是哪种模式。
5. **选择驱动方式**：有 Key 走 `runLive`，没有就走 `runReplay`。
6. **Agent 循环**（在线模式，`src/lib/agent/live.ts:26`）：
   - 调 Claude，流式接收思考和文字，每收到一小段就 `emit` 给前端；
   - Claude 说要调工具 → `emit({type:"tool_call"})`；
   - `runTool(name, input)` 执行 → `emit({type:"tool_result", summary, view})`；
   - 把结果（`forModel`）作为 `tool_result` 塞回对话，进入下一轮；
   - Claude 不再调工具时退出循环，最后发一个 `history` 事件。
7. **工具执行**：`src/lib/agent/tools.ts:459` 的 `runTool`：先用 zod **校验参数**，再调对应工具的 `run`。
8. **真正计算**：工具调用 `src/lib/fab/` 下的函数，比如 `analysis.ts` 的 `classifyWafer`（识别形状）、`commonality`（卡方检验）。
9. **前端读流**：`workbench.tsx` 的 `run()` 用 `reader.read()` 一块块读，按换行切开，每行 `JSON.parse` 成一个事件，交给 `onEvent`（`workbench.tsx:129`）。
10. **更新界面**：`onEvent` → `reducer`（`workbench.tsx:39`）更新状态 → React 重新渲染。工具卡片里的图表由 `src/components/views.tsx` 按 `view.kind` 分发到 `charts.tsx` / `wafer.tsx` 去画。

### 4.3 亲眼看看「流」长什么样

开着 `npm run dev`，另开一个终端：

```bash
curl -sN -X POST localhost:3000/api/agent \
  -H 'Content-Type: application/json' \
  -d '{"prompt":"N3B412 中心漏电","forceReplay":true}'
```

你会看到一行一行的 JSON 慢慢冒出来（这就是 **NDJSON**：每行一个 JSON），大概是：

```
{"type":"mode","mode":"replay","model":"离线回放"}
{"type":"thinking","delta":"先看 N3B"}        ← 思考过程，一小段一小段地来
{"type":"text","delta":"先看 "}               ← 正文文字
{"type":"tool_start","id":"replay_1","name":"get_lot_summary"}
{"type":"tool_call","id":"replay_1","name":"get_lot_summary","input":{"lot_id":"N3B412"}}
{"type":"tool_result","id":"replay_1","ok":true,"summary":"良率 ...","view":{...}}
...
{"type":"done"}
```

所有事件类型定义在 `src/lib/agent/types.ts` 的 `AgentEvent`。

### 4.4 单独调用一个工具（不需要启动网页）

我专门写了个小脚本 `scripts/try-tool.ts`：

```bash
npx tsx scripts/try-tool.ts list_lots '{}'
npx tsx scripts/try-tool.ts get_lot_summary '{"lot_id":"N3B417"}'
npx tsx scripts/try-tool.ts analyze_wafer_maps '{"lot_id":"N3B417"}'
npx tsx scripts/try-tool.ts commonality_analysis '{"bin":7,"threshold":0.06}'
npx tsx scripts/try-tool.ts query_equipment_log '{"tool_id":"ETCH-07","chamber":"C","start_date":"2026-10-10"}'
```

输出就是 Claude 真正收到的数据。试试故意传错：

```bash
npx tsx scripts/try-tool.ts get_lot_summary '{"lot_id":"N3B425"}'   # 在制批次 → TOOL_ERROR
npx tsx scripts/try-tool.ts get_lot_summary '{}'                     # 少参数 → INVALID_INPUT
npx tsx scripts/try-tool.ts hello '{}'                               # 没这个工具 → UNKNOWN_TOOL
```

这些错误在在线模式下会原样还给 Claude，Claude 读懂后会自己改参数重试。

### 4.5 一个工具的三种输出

每个工具的 `run` 返回三样东西（`tools.ts:19` 的 `ToolOutput`）：

| 字段 | 给谁 | 特点 |
| --- | --- | --- |
| `forModel` | Claude | **精简** JSON，只放推理需要的数字，省 token |
| `view` | 前端界面 | **丰富**数据，比如每颗 die 的 Bin，用来画图 |
| `summary` | 工具卡片 | 一句话结论 |

比如晶圆图工具：`view` 里有 25 片 × 626 颗 die 的完整 Bin 数据（用来画图），但 `forModel` 只告诉 Claude「每片是什么形状、置信度多少」。**AI 不需要看图，只需要看结论；人需要看图。**

## 6. 值得想明白的设计

读代码时可以思考这几个「为什么」：

1. **为什么要分 `forModel` / `view` / `summary`？**
   给 AI 的数据越多越贵、越慢，还容易让它分心；给人看的需要图。一份计算，三种呈现。

2. **为什么参数要用 zod 校验？**
   AI 偶尔会传错参数（比如 slot 填 30）。校验失败时，把错误信息还给 AI，它能自己纠正。这比程序直接崩溃好得多。见 `live.ts` 里 `is_error: true` 那段。

3. **为什么用「流」而不是等全部算完再返回？**
   一次完整调查要几十秒。流式输出让用户实时看到 AI 在想什么、在查什么，体验和信任感都好很多。

4. **为什么随机数是「确定性」的（`core.ts` 的 `rng`、`hashString`）？**
   用晶圆 ID 当种子，每次生成的数据一模一样。好处：可复现、可调试，演示时不会翻车，服务端和浏览器算出来也一致。

5. **服务端为什么不存对话？**
   每轮结束时服务端发一个 `history` 事件，把完整对话还给浏览器；下次追问时浏览器再带上。服务端是**无状态**的，简单，也好扩展。

6. **为什么要有回放模式？**
   演示现场可能没网、没 Key。回放保证 demo 一定能跑，而且工具计算依然是真的。

7. **隐藏答案（`HIDDEN_RULES`）为什么要隔离？**
   `core.ts:216` 写着「真正的故障是哪个腔体」。但只有**生成数据**的代码（`wafers.ts`、`metrology.ts`）会读它，分析和工具代码**从不读**。所以 Agent 是真的从数据里查出来的，不是作弊偷看答案。练习 4 会验证这一点。

```ts
const waferDetail = {
  name: "get_wafer_detail",
  description: "查看单片晶圆的良率和各 Bin 的 die 数量。用于确认某一片晶圆具体坏在哪里。",
  schema: z.object({
    lot_id: z.string().describe("批次号，如 N3B417"),
    slot: z.coerce.number().int().min(1).max(25).describe("槽位 1~25"),
  }),
  run({ lot_id, slot }: { lot_id: string; slot: number }): ToolOutput {
    const lot = requireTestedLot(lot_id);
    const w = lot.wafers.find((x) => x.slot === slot)!;
    const counts: Record<string, number> = {};
    for (const b of w.bins!) {
      const name = BINS[b as BinId].short;
      counts[name] = (counts[name] ?? 0) + 1;
    }
    return {
      forModel: { waferId: w.id, yield: +w.yield!.toFixed(4), binCounts: counts },
      summary: `${w.id} 良率 ${pct(w.yield!)}`,
    };
  },
};
```

**第 2 步**：把 `waferDetail` 加进 `TOOLS` 数组的末尾。
