# FAgent 学习指南（零基础版）

这份指南假设你：会一点编程（看得懂 if / for / 函数），但**不懂芯片制造，也没写过 Agent**。
跟着走完，你应该能讲清楚三件事：

1. 这个 demo 在解决工厂里的什么问题；
2. 一个「Agent」到底是怎么工作的；
3. 你在页面上点一下，代码里依次发生了什么。

## 2. 业务小白课：存储芯片工厂在查什么

### 2.1 晶圆和 die：一张披萨切成很多小块

- **晶圆（wafer）**：一张圆形的硅片，直径 300mm，像一张披萨。
- **die**：晶圆上切出来的一个个小方块，每块将来就是一颗芯片。本 demo 里每片晶圆有 **626 颗 die**（`src/lib/fab/core.ts` 的 `SITES`）。
- **DRAM**：内存芯片。每个存储单元 = **1 个晶体管 + 1 个电容**。电容里有电荷代表 1，没电荷代表 0。电容会慢慢**漏电**，所以内存要定时刷新。如果某个电容做坏了、漏得太快，刷新前数据就丢了，这叫**数据保持失效**。这是本 demo 主案例的「症状」。

### 2.2 批次、工序、设备、腔体

- **批次（lot）**：25 片晶圆装一个盒子，一起在工厂里走。批次号像 `N3B417`，片号是 1~25（槽位 slot），所以 `N3B417.03` 就是这盒的第 3 片。
- **工序（step）**：一片晶圆要经过几百道工序。demo 简化成 8 道（`core.ts` 的 `ROUTE`），比如「存储节点刻蚀」「CMP 研磨」「TiN 沉积」。
- **设备（tool）和腔体（chamber）**：一台设备（如 `ETCH-07`）里有好几个腔体（A、B、C）。同一批的 25 片晶圆会**轮流**进不同腔体：1 号进 A、2 号进 B、3 号进 C、4 号又进 A……
  - 所以如果你发现坏片总是「每隔几片坏一片」，就很可能是某一个腔体出了问题。

### 2.3 CP 测试、Bin、良率

- **CP 测试**：晶圆做完后，探针台逐颗 die 通电测试。
- **Bin**：测试结果分档。demo 用 8 档：

  | Bin | 含义 | 算好吗 |
  | --- | --- | --- |
  | 1 | 良品 | ✅ |
  | 2 | 修复良品（坏了几行，用备用行修好了） | ✅ |
  | 3 | 开路 / 短路 | ❌ |
  | 4 | IDD 漏电（静态电流过大） | ❌ |
  | 5 | 时序不过 | ❌ |
  | 6 | 阵列坏太多、修不好 | ❌ |
  | 7 | 数据保持失效（电容漏电） | ❌ |
  | 8 | 其他 | ❌ |

- **良率** =（Bin 1 + Bin 2）÷ 总 die 数。最近正常水平（**基线**）约 **91.2%**（`core.ts` 的 `BASELINE_YIELD`）。
- **Bin 柏拉图（Pareto）**：把各种坏法按数量排序的柱状图，一眼看出「主要坏在哪一类」。N3B417 是 Bin 7 特别多：12.6%，基线只有 1.1%。

### 2.4 晶圆图：坏点的「指纹」

把每颗 die 的 Bin 按位置涂色，就是**晶圆图（wafer map）**。坏点的**空间形状**往往直接暴露是哪类工艺出了问题：

| 形状 | 常见原因 | demo 里的场景 |
| --- | --- | --- |
| 边缘一圈（边缘环） | 刻蚀 / 沉积在晶圆边缘不均匀 | N3B417：刻蚀腔体边缘刻不够 |
| 弧形细线（划伤） | CMP 研磨时颗粒刮伤 | N3B409：研磨头划伤 |
| 中心一团 | 沉积喷淋头中间堵了 | N3B412：中心薄膜偏薄 |
| 随机散点 | 正常的随机缺陷 | 正常批次 |

- **叠加图（stacked map）**：把 25 片的晶圆图叠在一起，每个位置算「坏的比例」，形状会更清楚。
- **径向分布**：从圆心到边缘分几圈，每圈算坏的比例。边缘环的曲线会在最右边翘起来。

### 2.5 共性分析：卡方检验和 p 值（直觉版）

问题：坏片到底跟哪台设备、哪个腔体有关？

做法（`commonality_analysis` 工具）：

1. 把所有已测晶圆分两类：**坏片**（Bin 7 比例 > 6%）和**好片**。
2. 对每个腔体画一个 2×2 的表：

   |  | 坏片 | 好片 |
   | --- | --- | --- |
   | 经过 ETCH-07 C | 21 | 25 |
   | 没经过 | 0 | 204 |

3. 问：**如果这个腔体跟坏片完全无关，出现这种分布的概率有多大？** 这个概率就是 **p 值**。
   - 主案例 p ≈ 6.6×10⁻²⁴，意思是「纯属巧合」的可能性几乎为零。
   - 一般 p < 0.01 就算显著。
4. 卡方（χ²）就是计算这个 p 值的一种标准方法，不用背公式，记住「**p 越小，越不像巧合**」。

> ⚠️ p 值小只说明「相关」，不证明「因果」。所以 Agent 还要去查设备日志和量测，把**物理机理**补上。这就是「证据链」。

### 2.6 设备日志和在线量测

- **PM（预防性保养）**：定期拆开设备换零件。换完要做**复机认证（requalification）**：先跑一批测试片，确认没问题才能放产品进去。
- 主案例的故事就藏在日志里：10-14 腔体 C 换了**聚焦环**（一个套在晶圆边缘的环），复机时偷懒了：只跑了 25 片测试片（SOP 要求 50 片），也**没测边缘 CD**。
- **在线量测（inline metrology）**：生产中途抽测的数据。比如 `SN_BOTTOM_CD` 是存储节点孔底部的宽度。孔底太窄 → 电容做小了 → 存的电荷少 → 数据保持失效。
- Agent 会对比「10-14 之前 vs 之后」腔体 C 的边缘 CD，确认确实变窄了，而且**只在边缘**变窄。和晶圆图的边缘环对上了。

### 2.7 FA 和 8D 报告

- **FA（Failure Analysis，失效分析）**：工厂里对问题的正式调查。demo 里有个历史案例库（`src/lib/fab/knowledge.ts`），Agent 会翻「以前有没有类似的」。
- **8D 报告**：业界标准的问题处理报告，demo 只写其中 5 个 D：
  - **D2 问题描述**：什么批次、什么症状、掉了多少良率。
  - **D3 围堵**：马上止血。还在生产线上、经过了问题腔体的晶圆先扣住，别让它继续往下做。
  - **D4 根因**：为什么坏，附证据。
  - **D5 纠正**：怎么修好（比如重新校准、补做复机认证）。
  - **D7 预防**：以后怎么不再发生（比如把「复机必须测边缘 CD」写进 SOP）。

### 2.8 把主案例串起来（N3B417）

```
良率 78.6%（基线 91.2%） ── 哪类坏？ ──▶ Bin 7 数据保持，是基线的 11 倍
        │
        ▼ 坏在哪？
晶圆图：边缘一圈 ──▶ 怀疑刻蚀或沉积的边缘问题
        │
        ▼ 跟哪台设备有关？
共性分析：ETCH-07 腔体 C，p = 6.6×10⁻²⁴
        │
        ▼ 那台设备发生了什么？
日志：10-14 换聚焦环，复机认证不合规；之后有 RF 告警
        │
        ▼ 物理上说得通吗？
量测：10-14 之后腔体 C 边缘 CD 变窄，中心正常
        │
        ▼ 以前见过吗？
FA 案例库：有相同机理的老案例，当时的纠正措施可以参考
        │
        ▼ 还有谁受影响？
5 个在制批次共 46 片经过了问题腔体 → 立即拦截
        │
        ▼

```

**这就是一个良率工程师的标准思路，Agent 就是在模仿它。**

## 3. Agent 是什么

### 3.1 聊天机器人 vs Agent

- **聊天机器人**：你问一句，它凭记忆答一句。它没法查你工厂的数据库。
- **Agent**：你给它一个任务，它**自己决定**要查什么、调用哪个工具、看完结果再决定下一步，直到完成。

### 3.2 一个公式：Agent = LLM + 工具 + 循环

```
           ┌────────────────────────────────────────────┐
           │                                            │
 你的问题 ──▶  Claude 思考：「我该先查批次良率」             │
           │      │                                     │
           │      ▼ 输出一个「工具调用」请求                │
           │   get_lot_summary({lot_id: "N3B417"})      │
           │      │                                     │
           │      ▼ 我们的 TypeScript 代码真的去算        │
           │   { yield: 0.786, failBins: [...] }        │
           │      │                                     │
           │      ▼ 把结果还给 Claude                     │
           └──── Claude 再思考：「Bin 7 超标，看看晶圆图」 ◀┘
                  ...循环，直到 Claude 不再调用工具...
```

关键认知：**Claude 自己一个数都不算**。

- Claude 负责：**决定**下一步查什么、**解读**结果、**写**结论。
- 我们的代码负责：**真的去算**（读数据、做卡方检验、识别晶圆图形状）。

所以第 1 站那个问题的答案是：**图和数字是代码算的，查的顺序和文字结论是 AI 给的。** 这也是 Agent 可信的关键：数字可复现，不是 AI 编出来的。

### 3.3 工具 = 名字 + 说明 + 参数格式

Claude 怎么知道有哪些工具可用？我们每次请求都把「工具清单」发给它。每个工具三样东西（看 `src/lib/agent/tools.ts:47` 的 `listLots`）：

```ts
const listLots = {
  name: "list_lots",                          // 名字
  description: "列出 D1b LPDDR5 ... 所有批次……", // 说明：给 Claude 看的「使用说明书」
  schema: z.object({ status: ... }),          // 参数格式：用 zod 定义，自动转成 JSON Schema
  run({ status }) { ... },                    // 真正干活的函数（只在我们这边跑，Claude 看不到）
};
```

**description 写得好不好，直接决定 Claude 会不会用、用得对不对。** 它就是给 AI 的接口文档。

### 3.4 系统提示词 = 岗位说明书

`src/lib/agent/prompt.ts` 是一段约 30 行的中文，告诉 Claude：

- 你是谁（良率工程部的失效分析助手）；
- 背景知识（产品、Bin 定义、基线）；
- **调查方法**（8 步，和 2.8 节那张图一模一样）；
- 表达要求（调用工具前先说为什么、引用具体数字、不编数据）。

打开读一遍，你会发现它就像写给一个新入职工程师的培训材料。

### 3.5 两种模式：在线 vs 离线回放

| | 在线（live） | 离线回放（replay） |
| --- | --- | --- |
| 需要 | `ANTHROPIC_API_KEY` | 什么都不要 |
| 谁决定调哪个工具 | Claude 实时决定 | 剧本写死（`src/lib/agent/replay.ts`） |
| 工具结果 | **真实计算** | **真实计算**（同一个 `runTool`） |
| 能否追问 | 能 | 不能 |
| 代码 | `src/lib/agent/live.ts` | `src/lib/agent/replay.ts` |

**回放模式 = 用一段剧本「扮演」Claude**，但它调用的工具和在线模式完全是同一套。所以没有 Key 也能完整学习工具和前端部分。

## 4. 架构与一次请求的旅程

### 4.1 全景图

```
浏览器（React）                         服务器（Next.js）
┌──────────────────────┐   POST     ┌──────────────────────────────┐
│ workbench.tsx         │ ────────▶ │ app/api/agent/route.ts        │
│  run() 发请求          │           │   有 Key? ──是──▶ live.ts ◀──▶ Claude API
│  逐行读流 → onEvent    │ ◀──────── │          └─否──▶ replay.ts     │
│  reduce 更新界面       │  NDJSON 流 │                  │             │
│ views/charts/wafer    │           │                  ▼             │
│  画图                  │           │          agent/tools.ts runTool │
└──────────────────────┘           │                  │             │
                                    │                  ▼             │
                                    │   lib/fab/*（模拟工厂 + 统计）   │
                                    └──────────────────────────────┘
```

### 4.2 一次请求的 10 步（带文件位置）

以「点击 N3B417」为例：

1. **页面加载**：`src/app/page.tsx` 在服务端生成左侧批次卡片，并检查有没有 API Key（`liveAvailable`）。
2. **点击**：`src/components/workbench.tsx:152` 的 `run()` 被调用，把你的问题加入对话（`dispatch({type:"user"})`）。
3. **发请求**：`workbench.tsx:163` 用 `fetch("/api/agent")` 发 POST，body 是 `{prompt, history, turn, forceReplay}`。
4. **服务端接收**：`src/app/api/agent/route.ts:23` 的 `POST`。它创建一个**流**，先发一个 `{type:"mode"}` 事件告诉前端当前是哪种模式。
5. **选择驱动方式**：有 Key 走 `runLive`，没有就走 `runReplay`。
6. **Agent 循环**（在线模式，`src/lib/agent/live.ts:26`）：
   - 调 Claude，流式接收思考和文字，每收到一小段就 `emit` 给前端；
   - Claude 说要调工具 → `emit({type:"tool_call"})`；
   - `runTool(name, input)` 执行 → `emit({type:"tool_result", summary, view})`；
   - 把结果（`forModel`）作为 `tool_result` 塞回对话，进入下一轮；
   - Claude 不再调工具时退出循环，最后发一个 `history` 事件。
7. **工具执行**：`src/lib/agent/tools.ts:459` 的 `runTool`：先用 zod **校验参数**，再调对应工具的 `run`。
8. **真正计算**：工具调用 `src/lib/fab/` 下的函数，比如 `analysis.ts` 的 `classifyWafer`（识别形状）、`commonality`（卡方检验）。
9. **前端读流**：`workbench.tsx` 的 `run()` 用 `reader.read()` 一块块读，按换行切开，每行 `JSON.parse` 成一个事件，交给 `onEvent`（`workbench.tsx:129`）。
10. **更新界面**：`onEvent` → `dispatch` → React 调用 `reduce`（`workbench.tsx:39`）算出新状态 → React 重新渲染。工具卡片里的图表由 `src/components/views.tsx` 按 `view.kind` 分发到 `charts.tsx` / `wafer.tsx` 去画。

### 4.3 亲眼看看「流」长什么样

开着 `npm run dev`，另开一个终端：

```bash
curl -sN -X POST localhost:3000/api/agent \
  -H 'Content-Type: application/json' \
  -d '{"prompt":"N3B412 中心漏电","forceReplay":true}'
```

你会看到一行一行的 JSON 慢慢冒出来（这就是 **NDJSON 流**，4.6 节专门讲），大概是：

```
{"type":"mode","mode":"replay","model":"离线回放"}
{"type":"thinking","delta":"先看 N3B"}        ← 思考过程，一小段一小段地来
{"type":"text","delta":"先看 "}               ← 正文文字
{"type":"tool_start","id":"replay_1","name":"get_lot_summary"}
{"type":"tool_call","id":"replay_1","name":"get_lot_summary","input":{"lot_id":"N3B412"}}
{"type":"tool_result","id":"replay_1","ok":true,"summary":"良率 ...","view":{...}}
...
{"type":"done"}
```

所有事件类型定义在 `src/lib/agent/types.ts` 的 `AgentEvent`。

### 4.4 单独调用一个工具（不需要启动网页）

我专门写了个小脚本 `scripts/try-tool.ts`：

```bash
npx tsx scripts/try-tool.ts list_lots '{}'
npx tsx scripts/try-tool.ts get_lot_summary '{"lot_id":"N3B417"}'
npx tsx scripts/try-tool.ts analyze_wafer_maps '{"lot_id":"N3B417"}'
npx tsx scripts/try-tool.ts commonality_analysis '{"bin":7,"threshold":0.06}'
npx tsx scripts/try-tool.ts query_equipment_log '{"tool_id":"ETCH-07","chamber":"C","start_date":"2026-10-10"}'
```

输出就是 Claude 真正收到的数据。试试故意传错：

```bash
npx tsx scripts/try-tool.ts get_lot_summary '{"lot_id":"N3B425"}'   # 在制批次 → TOOL_ERROR
npx tsx scripts/try-tool.ts get_lot_summary '{}'                     # 少参数 → INVALID_INPUT
npx tsx scripts/try-tool.ts hello '{}'                               # 没这个工具 → UNKNOWN_TOOL
```

这些错误在在线模式下会原样还给 Claude，Claude 读懂后会自己改参数重试。

### 4.5 一个工具的三种输出

每个工具的 `run` 返回三样东西（`tools.ts:19` 的 `ToolOutput`）：

| 字段 | 给谁 | 特点 |
| --- | --- | --- |
| `forModel` | Claude | **精简** JSON，只放推理需要的数字，省 token |
| `view` | 前端界面 | **丰富**数据，比如每颗 die 的 Bin，用来画图 |
| `summary` | 工具卡片 | 一句话结论 |

比如晶圆图工具：`view` 里有 25 片 × 626 颗 die 的完整 Bin 数据（用来画图），但 `forModel` 只告诉 Claude「每片是什么形状、置信度多少」。**AI 不需要看图，只需要看结论；人需要看图。**

### 4.6 什么是 NDJSON 流（大白话版）

拆成两半讲。

**先说「流」。** 想象你在饭馆点了一桌菜：

- 方式 A：后厨把 8 个菜全做完，一次性端上来。你干坐 40 分钟，桌上什么都没有。
- 方式 B：做好一个菜就端一个。第 1 分钟上凉菜，第 5 分钟上热菜……你一直有东西吃。

方式 B 就是「流」：**数据不是一次性给你，而是一点一点陆续送过来。** AI 查一次要几十秒，用流的话，页面上的字一个个蹦出来、工具卡片一张张冒出来，而不是白屏等半天。

**再说「NDJSON」。** 菜一个一个上，每个菜得分得清。NDJSON（Newline-Delimited JSON，用换行分隔的 JSON）就是一种约定：**一条消息占一行，换行就代表这条结束了。**

对比一下普通 JSON：

```json
{"events": [{"type":"mode"}, {"type":"text","delta":"先看"}, {"type":"done"}]}
```

普通 JSON 是一个整体，少一个 `]` 都解析不了，必须全部收到才能用。NDJSON 每行独立：

```
{"type":"mode","mode":"replay"}
{"type":"text","delta":"先看"}
{"type":"done"}
```

收到一行就能解析一行，不用等后面的。

**合起来：NDJSON 流 = 服务器边干活边发消息，一条消息一行，浏览器收一行处理一行。**

### 4.7 流是怎么一段段传到界面的

把它想成一根水管：服务器往一头倒水，浏览器在另一头接。分 5 步。

**第 1 步：浏览器发请求，连接一直开着。**（`workbench.tsx:163`）

```ts
const res = await fetch("/api/agent", { method: "POST", body: ... });
```

这个 `await` **不会**等 AI 查完。服务器只要把响应开头（状态码 200、格式说明）发回来，它就往下走了。此时正文一个字都还没到，但连接开着。

**第 2 步：服务器立刻交出一根空水管。**（`route.ts`）

```ts
const stream = new ReadableStream({        // 造一根「水管」
  async start(controller) { ... }          // 往水管里倒水的逻辑（后台慢慢跑）
});
return new Response(stream, {              // 马上把水管作为响应返回
  headers: { "Content-Type": "application/x-ndjson" },
});
```

`return` 是**立刻**执行的，不等水管里有水；`start` 里的代码在后台继续跑。

**第 3 步：每有一个事件，就往管子里倒一行。**（`route.ts` 里的 `emit`）

```ts
const emit = (e: AgentEvent) => {
  controller.enqueue(encoder.encode(JSON.stringify(e) + "\n"));
};
```

- `JSON.stringify(e)`：事件对象 → 一行文字；
- `+ "\n"`：末尾加换行，这就是 NDJSON 的「一条一行」；
- `encoder.encode(...)`：文字 → 字节（网络只能传字节）；
- `controller.enqueue(...)`：塞进水管，Next.js 立刻通过 HTTP 连接发出去。

这个 `emit` 被**传给** `runLive` / `runReplay`。Agent 循环完全不知道 HTTP 是什么，它只管干活，有进展就调一下 `emit`。全部做完后发 `done`，再 `controller.close()` 关水管。

**第 4 步：浏览器一块一块地接。**（`workbench.tsx` 的 `run()`）

```ts
const reader = res.body.getReader();             // 拿到水管的出水口
for (;;) {
  const { done, value } = await reader.read();   // 等下一块数据（没到就一直等）
  if (done) break;                               // 水管关了 → 结束
  buf += decoder.decode(value, { stream: true }); // 字节变回文字，拼进缓冲区
  while ((nl = buf.indexOf("\n")) >= 0) {        // 缓冲区里每凑齐一行
    const line = buf.slice(0, nl);
    buf = buf.slice(nl + 1);
    onEvent(JSON.parse(line));                   // 解析，交给界面
  }
}
```

为什么要缓冲区 `buf`？因为网络按「块」送达，块的边界和行的边界对不上：

```
服务器发的：  {"type":"text","delta":"先看"}\n{"type":"done"}\n
实际送达：
  第 1 块：   {"type":"text","de
  第 2 块：   lta":"先看"}\n{"type":"do
  第 3 块：   ne"}\n
```

所以先攒着，**见到 `\n` 才算一行完整**，再解析；半截的留在 `buf` 里等下一块补齐。

**第 5 步：界面更新。** `onEvent` 把事件交给 React 更新页面（下一节细讲）。

整体时间线：

```
时间    服务器（route.ts）                            浏览器（workbench.tsx）
0.0s   收到请求，return 水管 ─────────────────────▶  fetch 返回，开始 reader.read() 等待
0.0s   emit(mode)        ── {"type":"mode"}\n ────▶ 页头显示「离线回放」
0.1s   emit(thinking)    ── {"type":"thinking"}\n ▶ 思考区冒出字
0.5s   emit(tool_start)  ── {"type":"tool_start"}\n ▶ 出现工具卡片（转圈）
1.4s   emit(tool_result) ── {"type":"tool_result"}\n ▶ 卡片完成，画出图表
 ...   （重复几十次）
30s    emit(done)，close() ────────────────────────▶  read() 返回 done，循环结束
```

### 4.8 `onEvent` 是怎么调到 `reduce` 的

注意：函数名叫 `reduce`（「reducer」是这类函数的统称）。`onEvent` 并不直接调用 `reduce`，而是调用 `dispatch(e)`，再由 **React** 去调用 `reduce`。两者是靠 `useReducer` 连起来的。

**第 1 步：`useReducer` 把两者绑在一起。**（`workbench.tsx:110`）

```ts
const [log, dispatch] = useReducer(reduce, { items: [], next: 1 });
```

把 `reduce` 函数和初始状态交给 React，React 还你两样东西：

| 拿到的 | 是什么 |
| --- | --- |
| `log` | 当前状态：对话里所有条目（用户的话、AI 的文字、工具卡片……） |
| `dispatch` | 「投递」函数：塞进一个事件，React 就会去调 `reduce` |

**第 2 步：`onEvent` 投递事件。**（`workbench.tsx:149`，`onEvent` 的最后一行）

```ts
dispatch(e);
```

**第 3 步：React 调用 `reduce` 算出新状态。** React 内部大致是：

```
新状态 = reduce(旧的 log, e)
把 log 换成新状态
重新渲染页面
```

`reduce`（`workbench.tsx:39`）格式固定：**输入「旧状态 + 一个事件」，返回「新状态」**，用 `switch (a.type)` 分情况：

```ts
function reduce(s: LogState, a: Action): LogState {
  switch (a.type) {
    case "text":        // 最后一条也是文字 → 接到末尾；否则新开一条
    case "tool_start":  // 新加一张工具卡片，状态 running（转圈）
    case "tool_result": // 按 id 找到那张卡片，改成 ok，填上 summary 和 view
    ...
  }
}
```

**例子：AI 说「先看 N3B412」**，服务器分 3 行送来 `"先看 "`、`"N3B"`、`"412"`，每行都走一遍 `onEvent → dispatch → reduce`：

| 第几次 | 旧状态最后一条 | `reduce` 做的事 | 新状态最后一条 |
| --- | --- | --- | --- |
| 1 | 用户的问题 | 不是文字，新开一条 | 文字「先看 」 |
| 2 | 文字「先看 」 | 是文字，接上去 | 文字「先看 N3B」 |
| 3 | 文字「先看 N3B」 | 接上去 | 文字「先看 N3B412」 |

每次状态变，React 都重画，所以你看到字一点点长出来。

**完整链路：**

```
reader.read() 收到一行 JSON
  → JSON.parse 变成对象
  → onEvent(e)                   workbench.tsx:129
  → dispatch(e)                  workbench.tsx:149
  → React 调用 reduce(旧状态, e)   workbench.tsx:39
  → 返回新状态，React 存下来
  → React 重新渲染，页面更新
```

**为什么不在 `onEvent` 里直接 `log.items.push(...)`？**

1. **React 察觉不到。** 直接改数组，React 不知道数据变了，页面不会刷新。必须通过 `dispatch`（或 `setState`）告诉它。
2. **规则集中。** 「事件怎么改变页面」全写在 `reduce` 一个函数里，想知道收到 `tool_result` 时页面怎么变，只看那一个 `case`。

这也是 `reduce` 里都写 `[...s.items, 新条目]` 而不是 `push` 的原因：每次**生成新数组**而不是改旧数组，React 靠「新旧是不是同一个对象」判断有没有变化。

**不是所有事件都进 `reduce`。** `onEvent` 在 `dispatch` 之前先拦下几种：

- `mode`：存进 `setMode`（页头的「在线 / 离线回放」），直接 `return`；
- `history`：存进 `historyRef`，留给下次追问时带给服务器，直接 `return`；
- `done`：什么都不做，`return`；
- 带晶圆图的 `tool_result`：额外更新中间舞台的晶圆图（`setMaps`），**然后照样** `dispatch`，因为日志里的卡片也要更新。

**自己验证：** 在 `reduce` 第一行加 `console.log("reduce 收到：", a.type, a);`，浏览器按 F12 切到 Console，点一个批次，就能看到每个事件依次经过 `reduce`。看完删掉。

### 4.9 `history`：AI 的「记忆」是怎么来的

**先记住一个事实：Claude API 本身没有记忆。** 每次调用都是一次全新的请求，它不记得上一次你们聊过什么。要让它「接着聊」，唯一的办法是**每次把之前的完整对话一起发过去**。所谓多轮对话，其实是每次都把整本聊天记录重新交给它读一遍。

**`history` 就是这本「聊天记录」。** 它是 Anthropic API 要求的 `messages` 数组。一轮调查结束后，大概长这样：

```js
[
  { role: "user",      content: "N3B417 良率掉到 80% 以下了，帮我查一下根因…" },
  { role: "assistant", content: [ 思考块, 文字「先看批次概况」, tool_use{id:"toolu_01", name:"get_lot_summary", input:{lot_id:"N3B417"}} ] },
  { role: "user",      content: [ tool_result{tool_use_id:"toolu_01", content:"{良率 66.6%…}"} ] },
  { role: "assistant", content: [ 文字「数据保持失效偏高…」, tool_use{id:"toolu_02", name:"analyze_wafer_maps", …} ] },
  { role: "user",      content: [ tool_result{tool_use_id:"toolu_02", …} ] },
  …（十几个来回）
  { role: "assistant", content: [ 文字「根因是 ETCH-07 腔体 C…」 ] }
]
```

注意：**工具结果是以 `role: "user"` 的身份发回去的**。这是 API 的约定：AI 说「我要调工具」，「用户这一方」（也就是我们的程序）执行完后把结果交回去。里面放的是工具的 `forModel`，不是画图用的 `view`。

**一次追问的完整来回：**

```
第 1 轮（点「N3B417」）
  浏览器：history = []（空），发 { prompt: "N3B417 良率掉…", history: [] }
  route.ts:43     把新问题接在 history 后面 → [用户问题]
  live.ts:23      复制一份作为 messages，进入循环
  live.ts 循环中  每轮 messages.push(AI 回复)、messages.push(工具结果)，越来越长
  live.ts:94      循环结束：emit({ type: "history", messages })  ← 整本记录发回浏览器
  浏览器 :132     historyRef.current = e.messages               ← 浏览器替你保管

第 2 轮（追问「为什么排除了腔体 A？」）
  浏览器 :166     发 { prompt: "为什么排除了腔体 A？", history: historyRef.current }
  route.ts:43     [第 1 轮全部记录…, 新问题]
  Claude          读到了上一轮所有工具结果，所以能直接回答，不用重查
  live.ts:94      再把更长的记录发回来，浏览器替换保管
```

**「无状态」是什么意思？** 服务端处理完一次请求就什么都不留，下一次请求的所有信息全部由请求本身带来。打个比方：

- **有状态**：医院把你的病历存在档案室。你每次只报名字，医生去档案室调。档案室得有人管理、要备份；换一家分院，那边没有你的档案。
- **无状态**（本 demo）：病历本你自己揣着，每次看病交给医生，看完医生写上新内容还给你。医院什么都不存，你去任何一家分院都能接着看。

| | 无状态（本 demo） | 有状态（服务端存对话） |
| --- | --- | --- |
| 服务端要做的 | 什么都不存 | 要数据库或内存，要按会话 ID 查找、过期清理 |
| 多台服务器 / 重启 | 随便哪台都能处理，重启不丢 | 要共享存储，否则换台机器就「失忆」 |
| 每次请求的大小 | 越聊越大（记录里含所有工具结果） | 只发新问题，很小 |
| 记录能否被篡改 | 浏览器能改，服务端只能照单全收 | 服务端说了算 |
| 刷新页面 | 记录丢失（只存在内存里） | 可以恢复 |

所以无状态适合 demo：代码最少，部署最简单。真上生产，通常会把对话存到服务端数据库，或至少对记录做签名防篡改。

**几个容易混的点：**

1. **`history` 和界面上的对话 `log` 是两份东西。** `log.items` 给人看：文字按碎片拼起来，工具卡片带画图用的 `view`。`history` 给 Claude 看：API 规定的格式，工具结果是精简的 `forModel`。两份各管各的，浏览器从不打开 `history` 看内容，只是原样保管、原样送回（里面的思考块带有签名，改了 API 会拒收）。
2. **为什么用 `useRef` 而不是 `useState` 存？** 它不显示在界面上，换了也不需要重新渲染。`useRef` 就是一个「改了不触发刷新」的小盒子。
3. **中途停止或出错时，这一轮不进记忆。** 停止或出错时 `runLive` 会抛出异常，走不到最后的 `emit({type:"history"})`，所以 `historyRef` 还是上一轮的版本。下次追问会接着上一轮完整的记录，不会带上半截对话。
4. **回放模式不发 `history`。** 回放是写死的剧本，用不上 Claude 的记忆。它靠 `turn`（第几轮）判断：`turn > 0` 又没提批次号，就回复「离线回放不能自由追问」（`replay.ts:329`）。
5. **点「新调查」**（`reset`，`workbench.tsx:196`）会把 `historyRef` 清空、`turn` 归零，相当于换一本新的病历本。

**自己验证：** 配好 API Key，调查完一个批次后，在 DevTools 的 Network 面板里找 `agent` 请求，看最后一行 `{"type":"history",…}` 有多长。再追问一句，看第二次请求的 Payload：`history` 里就是第一轮的全部内容。

## 6. 值得想明白的设计

读代码时可以思考这几个「为什么」：

1. **为什么要分 `forModel` / `view` / `summary`？**
   给 AI 的数据越多越贵、越慢，还容易让它分心；给人看的需要图。一份计算，三种呈现。

2. **为什么参数要用 zod 校验？**
   AI 偶尔会传错参数（比如 slot 填 30）。校验失败时，把错误信息还给 AI，它能自己纠正。这比程序直接崩溃好得多。见 `live.ts` 里 `is_error: true` 那段。

3. **为什么用「流」而不是等全部算完再返回？**
   一次完整调查要几十秒。流式输出让用户实时看到 AI 在想什么、在查什么，体验和信任感都好很多。

4. **为什么随机数是「确定性」的（`core.ts` 的 `rng`、`hashString`）？**
   用晶圆 ID 当种子，每次生成的数据一模一样。好处：可复现、可调试，演示时不会翻车，服务端和浏览器算出来也一致。

5. **服务端为什么不存对话？**
   每轮结束时服务端发一个 `history` 事件，把完整对话还给浏览器；下次追问时浏览器再带上。服务端是**无状态**的，简单，也好扩展。详见 4.9 节。

6. **为什么要有回放模式？**
   演示现场可能没网、没 Key。回放保证 demo 一定能跑，而且工具计算依然是真的。

7. **隐藏答案（`HIDDEN_RULES`）为什么要隔离？**
   `core.ts:216` 写着「真正的故障是哪个腔体」。但只有**生成数据**的代码（`wafers.ts`、`metrology.ts`）会读它，分析和工具代码**从不读**。所以 Agent 是真的从数据里查出来的，不是作弊偷看答案。练习 4 会验证这一点。

### ⭐⭐⭐ 练习 5：加一个新工具 `get_wafer_detail`

目标：让 Agent 能查「单片晶圆各 Bin 的 die 数量」。

**第 1 步**：在 `src/lib/agent/tools.ts` 里，`report` 工具后面、`TOOLS` 数组前面加：

```ts
const waferDetail = {
  name: "get_wafer_detail",
  description: "查看单片晶圆的良率和各 Bin 的 die 数量。用于确认某一片晶圆具体坏在哪里。",
  schema: z.object({
    lot_id: z.string().describe("批次号，如 N3B417"),
    slot: z.coerce.number().int().min(1).max(25).describe("槽位 1~25"),
  }),
  run({ lot_id, slot }: { lot_id: string; slot: number }): ToolOutput {
    const lot = requireTestedLot(lot_id);
    const w = lot.wafers.find((x) => x.slot === slot)!;
    const counts: Record<string, number> = {};
    for (const b of w.bins!) {
      const name = BINS[b as BinId].short;
      counts[name] = (counts[name] ?? 0) + 1;
    }
    return {
      forModel: { waferId: w.id, yield: +w.yield!.toFixed(4), binCounts: counts },
      summary: `${w.id} 良率 ${pct(w.yield!)}`,
    };
  },
};
```

**第 2 步**：把 `waferDetail` 加进 `TOOLS` 数组的末尾。

**第 3 步**：在 `src/lib/agent/labels.ts` 加一行中文名：`get_wafer_detail: "单片晶圆详情",`

**第 4 步**：测试

```bash
npx tsx scripts/try-tool.ts get_wafer_detail '{"lot_id":"N3B417","slot":3}'
# 预期：N3B417.03 良率 66.6%，数据保持 143 颗……
```

## 10. 自测题

能答出来，就算学会了：

1. N3B417 的根因是什么？Agent 用了哪几类证据？为什么光有 p 值还不够？
2. Claude 在这个 demo 里**不做**哪些事？如果它算错了一个数，会发生什么？
3. 一个工具的 `forModel` 和 `view` 有什么区别？为什么要分开？
4. 用户点击按钮后，数据依次经过了哪些文件？（至少说出 5 个）
5. 要加一个新工具，最少要改几个地方？Claude 是怎么知道新工具存在的？
6. 浏览器读流时为什么要有缓冲区 `buf`？`onEvent` 为什么不直接改 `log.items`，而要 `dispatch`？

<details>
<summary>参考答案（先自己想）</summary>

1. ETCH-07 腔体 C 换聚焦环后复机不合规，边缘刻蚀不足 → 存储节点孔底边缘偏窄 → 电容小 → 数据保持失效。证据：Bin 柏拉图、晶圆图边缘环、共性分析、设备日志、在线量测、历史 FA 案例。p 值只证明相关，需要日志和量测补上物理机理（因果）。
2. 不算数、不读数据库、不画图。数字都由工具算，Claude 只决定查什么、解读、写结论。它若误读了数字，结论会错，但原始数字可追溯（工具卡片里都有），人可以核对。
3. `forModel` 是给 AI 的精简 JSON（省 token、聚焦），`view` 是给界面画图的完整数据。
4. `workbench.tsx` → `api/agent/route.ts` → `live.ts` 或 `replay.ts` → `tools.ts` → `fab/analysis.ts`、`fab/wafers.ts` 等 → 流回 `workbench.tsx`（onEvent → dispatch → reduce）→ `views.tsx` → `charts.tsx` / `wafer.tsx`。
5. 最少 2 处：`tools.ts` 里定义对象并加进 `TOOLS`、`labels.ts` 加中文名（不加也能跑，只是卡片显示英文名）。`toolDefinitions()` 每次请求都把工具清单发给 Claude。
6. 网络按块送达，一块可能只有半行 JSON，直接解析会报错；先攒进 `buf`，见到 `\n` 才解析完整的一行。直接改数组 React 察觉不到、页面不刷新；`dispatch` 让 React 调用 `reduce` 生成新状态并重新渲染，状态变化规则也集中在 `reduce` 一处。

</details>
